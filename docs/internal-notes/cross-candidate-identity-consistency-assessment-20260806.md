# 跨维度一致性调查：间接提及 × 别名 / 已有身份（2026-08-06）

只调查、不写生产代码、不加金标。

## 1. 悦安案例：机制分析

### 剧本事实（`01_echo_inn_long.txt`）

- 抽取人物含 **林悦**（bio/speaker，在场）。
- 录音与对白：`「悦安」` + 林悦当场说「他叫我悦安」。
- 语义上：悦安 = 林悦的小名/别名，不是新角色。

### 间接提及侧（今天 live e2e，flag on）

| 步骤 | 行为 |
|---|---|
| Discovery | `quoted_name` 命中「悦安」；`already_extracted_as_character=false`（悦安不是抽取 canonical 名） |
| LLM 判断 | `refers=true`, `present=false` → 产出间接提及候选 |
| review_action | **固定** `use_core_asset_command_create_manual_character` |
| 与别名模块 | **零感知**：builder 不读 `alias_link_proposals`，也不读已有资产的 `aliases` |

### 别名侧（同一剧本，确定性规则）

| 步骤 | 行为 |
|---|---|
| 抽取锚点 | `老周, 苏晴, 林悦, 陈默, 苏衡` |
| 实际提案 | **仅** `陈默 ↔ 陈师傅`（`surname_title_same_scene`） |
| 林悦 ↔ 悦安 | **不产出** |

原因（规则边界，不是 bug）：

- `given_name_suffix` 要求锚点 **3–4 字**（`林悦安`→`悦安` 是 A4 金标形态）；`林悦` 只有 2 字，后缀规则直接跳过。
- 脚本没有 `林悦（小名「悦安」）` 这种 `explicit_aka_label` 形态；「他叫我悦安」是叙事/对白推理，确定性规则刻意不做。

### 结论（悦安）

这不是「两个候选系统同时提出悦安、互相打架」的双提案冲突。  
更准确说是：

1. **别名系统对这条剧本沉默**（规则覆盖不到「2 字全名 + 对白自认小名」）；
2. **间接提及把悦安当成可新建角色的候选**；
3. 两边 **互不感知**；人工若按 `create_manual_character` 确认，会造出与林悦平行的第二身份。

LLM 其实在 reason 里承认「林悦确认他叫我悦安」，但仍给 `present=false`，并走「新建角色」动作——**判断语义与确认动作错配**。

## 2. 风险真实范围（常见程度）

在今天验证过的 5 个剧本上做只读交叉探针 + live 提案对照（两开关的数据能力，不是新跑 LLM）：

| 类型 | 定义 | 5 剧本中出现 | 例子 |
|---|---|---|---|
| A. 与别名**提案表面**字符串撞车 | discovery/mention ∈ alias_link_proposals.alias | **0 / 5** | （无） |
| B. 与已抽取 **canonical 名** 同字 | mention ∈ named_characters，仍被判间接提及 | **2 / 5** | 苏衡（echo）、陈默（night） |
| C. 上下文可断为已知人别名，但规则链不上 | 对白/录音自认等 | **1 / 5** | 悦安↔林悦 |
| D. 疑似小名/爱称，无规则、仅叙事 | 人名形，需人读 | **1 / 5** | 晚晚（信里写给顾晚） |
| E. 真·未出场新身份（设计目标） | 金标 I1 | **4 / 5** 有 | 顾衡 / 沈岚 / 江澄 / 柯衡 |

### 严重程度判断（不夸大）

- **不是**「一开间接提及就必炸」：真正新身份（E）仍是主产物；与别名提案的**直接字符串冲突（A）在本样本为 0**。
- **但是**，一旦开付费开关，**长剧本上几乎总会混进若干「不该新建」的人名形候选**（B/C/D）。本样本约 **2/5 有 B，1–2/5 有 C/D**，且与 E 同批出现。
- **自动权威化路径不存在**：重复身份只有在人执行 `create_manual_character` 时才会落库。风险是 **确认 UX 把人推向「新建」且无警示**，不是静默写坏。
- 特别扎眼的工程事实：discovery 已写 `already_extracted_as_character`，提案也带出该字段，但 **emit / review_action / confirm 完全不用它**。苏衡、陈默这类 **最便宜可挡的重复** 今天仍会进候选列表。

隐蔽层级（由易到难）：

1. **易（可机械查）**：mention == 某资产 `display_name` / `name`（苏衡、陈默）。
2. **中（可机械查，依赖别名已确认或别名提案）**：mention ∈ `aliases` 或 ∈ 当前 `alias_link_proposals`。
3. **难（当前系统看不到）**：悦安式——字符串两边都没登记成别名，只靠对白推理；或晚晚式——爱称与 canonical 无子串/后缀关系。

## 3. 现有确认路径有没有查重

### `create_manual_character`（`runtime_script_core_truth._preview_core_asset_command`）

查过实现，**没有**下列任何检查：

- 同 revision 是否已有同名 `character` 资产；
- 是否命中任何角色的 `aliases`；
- 是否命中当前 candidate 上的 `alias_link_proposals`；
- 是否尊重提案上的 `already_extracted_as_character`。

行为摘要：

- 只要求 `display_name` / `name` / `mention` 非空；
- `asset_id = hash(project:revision:manual:name:now)` → **连同名二次创建也不会因 id 碰撞失败**；
- preview → confirm 直接落 `status=confirmed` 的新角色。

与 `merge_alias` 对比：后者至少要求目标是已有 character；**没有**「这个 alias 是否已是另一人的名字」的交叉守卫，但也不是新建整身份。

**结论：确认前查重目前不存在**（不是「有但没注意到」）。

### 技术可行性（若以后做，仅评估）

| 检查点 | 可行性 | 风险 |
|---|---|---|
| confirm/preview 时扫本 revision 角色的 name+aliases，精确匹配则 **warn 或 409** | 高；纯内存字典 | 低；误伤少 |
| 同时扫本 candidate 的 `alias_link_proposals` | 高；但两 flag 常不同时开 | 中：flag 组合态要定义 |
| 把 `already_extracted_as_character` 改成禁止 create / 改 review_action→merge_alias | 高 | 中：苏衡可能是「引号里再提已出场者」，禁新建合理；改 merge 需目标资产 |
| 用 LLM 推断「是否已知人别名」 | 能做 | **高成本/高不稳**；不适合作为第一道闸 |

最小防护若只做「精确命中 name/aliases → 确认前警示或拒绝新建」，**技术简单、回归面小**。

## 4. 要不要建跨维度一致性评测 / 防护

### 建议（优先级）

| 项 | 建议 | 理由 |
|---|---|---|
| **确认前精确查重（name + aliases）** | **值得做，且应优先于大评测** | 挡住 B 类（苏衡/陈默）与「别名已确认后再确认间接提及」；实现小、不夸大问题也能立刻降风险 |
| **提案层：already_extracted 时不要推 create_manual_character** | **值得做（小改）** | 字段已在；今天浪费信号 |
| **完整「跨维度」评测框架** | **暂缓大框架；可先 1–2 个探针用例** | 样本里 A 类（双提案同字）稀少；悦安类难自动判金标，容易做成提示词考古 |
| **用 LLM 解悦安式别名在场** | **这次仍不建议当主防护** | 已验证不稳定；应落在人工确认 + 查重警示，而不是再加一层自动权威 |

### 若只做最小评测探针（不是现在落金标，仅描述形状）

1. **P1 精确重复**：剧本已有 speaker「苏衡」，另有引号「苏衡」被判间接提及 → 期望：不得无警示地 `create_manual_character` 成功（或提案不应指向新建）。
2. **P2 悦安式上下文别名**（手工断言）：林悦在场 +「他叫我悦安」+ 悦安间接候选 → 期望：至少警示「可能是林悦别名」，或 review_action 不是裸新建；**不要求**系统自动 merge。
3. **P3（可选）双提案同字**：刻意用 `林悦安`+对白`悦安`（A4）再加一处仅引号、无 speaker 证据的「悦安」——仅当间接提及仍提案时，断言与 alias 提案同表面应有冲突标记。

P1 性价比最高；P2 是悦安真实风险的回归钉，但断言要写成「警示/动作」，不要写成「必须识别别名」。

### 不值得现在投入的

- 把「候选互相冲突」做成与别名/缺失证据同级的完整维度（新 schema、宏平均、coverage 哲学）——**过早**：当前主缺口是确认路径零查重 + 已有字段未用，不是缺少一套 F1。
- 为夸大交叉冲突而堆很多「双系统同提一字」的金标——在真实长剧本上这类 **少见**；更常见的是 B/C。

## 5. 总评

| 问题 | 答案 |
|---|---|
| 悦安是不是两系统同时认出来的冲突？ | **不是。** 别名系统对本剧沉默；间接提及单方面当新角色候选。 |
| 有没有更隐蔽的冲突？ | **有**：上下文别名（悦安）、爱称（晚晚）；以及更机械的 **已抽取同名仍提案**（苏衡/陈默）。 |
| 常见吗？ | **开功能后中等常见、但非必发灾难**：本样本约半数长剧会混入危险候选；**默认关 flag 时生产无事**；且无自动落库。 |
| create_manual_character 有查重吗？ | **没有。** |
| 下一步 | **先做确认前精确查重 + 用好 already_extracted**；跨维度评测先用 1–2 探针钉住，不必先建完整维度。 |
