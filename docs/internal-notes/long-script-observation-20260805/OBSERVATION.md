| 苏衡 | 靠录音段落的独立行 speaker cue「苏衡」抓到（意外但合规则） |

| 漏 / 未成候选 | 归因 |
|---|---|
| 「陈师傅」 | 对白称呼 → **别名**，非长文新逻辑 |

## 3. 问题归因：长度本身 vs 已知问题放大

### 3.1 表现是否「意外地还不错」？

**在「行业 heading + 标签/speaker 纪律内」：是的，意外地稳。**

- 主场景列表完整、少 junk。
- 主创人物大多能进候选。
- 全文单次扫描在 3k 字级无性能问题。
- 同名场景回访靠精确去重，行为可预期。

### 3.2 长文暴露了什么？

| 观察 | 更像 |
|---|---|
| 陈师傅 / 周叔 / 悦安 / 方恬 | **别名**（已开题）放大：人多、称呼多 |
| 顾衡只在信件/叙事 | **间接提及 I1**（已判暂缓）放大 |
| 刘正 vs 站长刘正 | 别名/bio 粘连，短篇也可有，长文 bio 更多更易撞 |
| 邮局大厅全称 vs 简称；合租屋两种写法 | **长文+混排更易出现的近义场景双候选** —— 这是较接近「长文独有」的现象，但是 **命名一致性/归一** 问题，不是「太长扫不动」 |
| 录音 speaker 抓到苏衡 | 规则副作用，短篇也可，长文录音/闪回更多所以更常见 |

**没有看到的「长文独有灾难」：**

- 无 200k 相关行为
- 无超时、无内存迹象（此规模）
- 无「场数一多就整表 missing」
- 无分块缺失导致的前后矛盾（本来也无分块）

### 3.3 判断（对应你的第 3 点要求）

**长剧本目前不是一个该单独优先「攻坚」的提取内核问题。**

更准确的说法：

1. **长度本身（3k 字 / 12 场）** 对确定性提取器主要带来线性变慢（仍可忽略）和 **更多机会触发已知弱点**。
2. 真正伤理解质量的，仍是 **别名、间接提及（发现）、混排下的场景别名/近义名**；把「长剧本」当独立特性去加分块/滑窗，**解决不了**顾衡漏召回或刘正双候选。
3. 较接近长文独有的是 **跨场同地异名、全称/简称并存** → 可将来做成「场景身份链接」小题，但应跟别名同一类「身份归一」，而不是「长文本引擎」。
4. 真·剧集量级（远超 6k、近 20 万）的分块/记忆尚未测试；**本次不外推**。若要测上限，需另造近上限语料；预期瓶颈仍可能是规则假阳性累积，而不只是毫秒数。

## 4. 建议（不实施，仅记录）

- **语料：** 本目录两份可留作回归用长文；不必立刻扩到 200k。
- **工程优先级：** 继续别名提案 / 缺失证据评测；间接提及维持暂缓。
- **长文：** 暂不单独立项改提取器；若做，优先「场景近义归一」评测小题，而非分块框架。

## 5. 一句话

**现有提取器在真·短剧长度（~3k 字、12 场）上结构提取大体可用、性能无忧；长文主要放大别名/间接提及/近义场景名等已知问题，而不是暴露必须立刻单独解决的「长文本引擎」新问题。**
