# AFS 仓库收敛与迁移矩阵 v0.1

日期：2026-08-04
状态：执行草案；用于当前集成、任务分配和迁移决策，不代表发布验收。

## 1. 当前共同目标

一个月目标不是把所有历史功能一次性搬完，而是交付一条可真实操作、可追溯、可恢复的智能制作纵切：

1. 导入或编写剧本，形成不可变剧本版本；
2. 无 Provider 的基础提取或受控智能分析产生候选；
3. 人工核对证据并编辑、确认或拒绝；
4. 只有确认事实进入 Production Graph；
5. 确认事实继续进入场景、资产和镜头计划；
6. 至少一种媒体生产任务能走完预检、提交、进度、失败恢复和结果回收；
7. 刷新或重启后，剧本版本、审阅决定、图关系和任务状态不丢失。

这条纵切是第一版智能化 AFS 的 MVP。多模态质量、规模化 SaaS、商业验证和正式发布仍是后续独立门槛。

## 3. 当前两份工程提交的归并结论

### PR #228：全栈审阅骨架

保留为产品主骨架，负责：

- Script Core Truth 与不可变剧本版本；
- 单一候选、资产版本和人工审阅生命周期；
- 编辑、确认、拒绝、过期、幂等和失败恢复；
- Production Graph 写入；
- Studio 审阅界面和浏览器恢复验证。

不再另建第二套候选账本、第二套审阅 API 或第二套 Studio 状态机。

### PR #229：智能理解机制捐赠源

保留为选择性吸收的机制源，优先吸收：

- 更保守的人物/场景提取；
- `extracted_from_text / model_inferred / missing / conflicting` 等证据认识状态；
- 精确证据 span 和缺失信息的诚实表达；
- Profile、Beat、Format、Scene cast、Prop 等后续候选类型的验证经验；
- revision ID、Graph 幂等恢复和失败可重试等已验证修复。

不直接吸收：

- 与 PR #228 重复的账本、API、UI 和 Graph 投影；
- 默认关闭后长期无人负责的开关堆叠；
- 尚无可靠证据的连续性、镜头或制作可行性判断；
- 只存在于文档、未进入产品链路的完成声明。

### 当前统一分支

隔离分支 `codex/candidate-review-convergence-20260804` 以 `origin/master @ 272d4114` 为基线，已吸收 PR #228，并把第一批无 Provider、可追溯提取接入同一审阅闭环。它是集成候选，不是新的长期分叉。

## 5. 每次工程提交的统一集成流程

1. 工程师先推远程分支或 Draft PR，不再以“本地完成”作为交付；
2. 集成负责人记录基线、精确 HEAD、改动范围、测试和非声明；
3. 在隔离工作树中评估，不直接污染主仓或服务器运行目录；
4. 先确认功能归属：保留、选择性吸收、暂缓或删除；
5. 先跑专项回归，再跑相关全栈测试和完整 CI；
6. HEAD 变化后，旧的 PASS 自动失效；
7. 形成新的 Draft 集成 PR，由独立评估结果决定是否进入 `master`；
8. 合并、部署、Provider smoke、人工验收和业务验证分别记账，不能互相替代。

## 6. 三人协作安排

### 集成负责人（项目 Owner，同时参与开发）

- 每次接收提交后完成精确 HEAD 集成、冲突裁决和证据收口；
- 亲自承担跨前后端的小纵切和智能体协议适配，避免只做项目管理；
- 维护本矩阵、MVP 验收清单和 Integration Queue；
- 每天只保留一个主阻塞点，每周至少形成一个可演示的端到端增量。

### 智能体工程师

- 先把 PR #229 修到精确 HEAD CI 终态通过；
- 在统一分支评审完成前暂停扩新类型；
- 下一批以“适配现有审阅闭环”为任务，不再扩第二套账本；
- 优先交付离线评测语料、证据/缺失/冲突契约，以及受控模型候选接口；
- 每个提交必须含远程分支、精确 HEAD、真实失败样例和回归测试。

### 全栈工程师

- PR #228 暂作为已交付骨架，不在原分支继续平行扩张；
- 当统一 Draft PR 提供稳定的提取 API 与 Studio 入口后重新接入；
- 第一任务是把“提取—审阅—确认—Graph—刷新恢复”做成清晰产品流程；
- 第二任务是从 V3/DG 对照迁入一种媒体任务的成熟前后端机制；
- 不重写智能提取规则，不另建候选状态机。

## 7. 一个月执行节奏

### 第 1 周：收敛和清障

- PR #229 精确 HEAD CI 归零；
- 统一候选闭环 Draft PR 建立并通过测试；
- 冻结单一 revision、candidate、asset、Graph ID 关系；
- 选定 V3/DG 的第一种媒体任务作为迁移样板。

### 第 2 周：剧本到生产计划纵切

- 人物、场景、Scene cast、核心道具进入同一审阅闭环；
- 确认事实驱动场景/资产需求和镜头计划；
- 受控智能体只读取权威事实，并输出可审阅计划与回执。

### 第 3 周：成熟全栈机制接入

- 接通一种媒体任务的预检、提交、进度、重试和结果回收；
- 补齐工作区、资产库和任务状态的产品体验；
- 做一次禁 Provider 的完整回放和一次单独授权的 Provider smoke（若届时获得授权）。

### 第 4 周：可靠性、体验与演示

- 修复刷新、重启、重复提交、版本变化和部分失败问题；
- 完成桌面/移动浏览器验收和代表性剧本演示；
- 形成 V2 首批迁移包及保留/删除清单；
- 只对已取得证据的范围声明 MVP 完成。

## 8. 首批写入 V2 前的门槛

只有同时满足以下条件，才开始 V2 首批迁移：

- 当前统一 Draft PR 有终态 CI 和专项评估；
- revision、candidate、asset、Graph ID 权威已确定；
- V2 当前功能分支 `codex/v2-script-proposal-slice` 的去留已形成明确决策；
- 首批迁移是一个可闭合纵切，而不是散落文件搬运；
- 明确哪些机制来自 AFS、V3/DG、DramaStudio，且没有复制不必要的身份/壳层；
- 有回滚、数据兼容和临时分支清理方案。

V3/DG 在 V2 完成纵切、迁移验证和人工验收前继续保留，不做提前退役。

## 9. 当前非声明与待决策

- 当前成果不是生产部署、Provider 质量验收、人工产品验收或业务验证；
- DramaStudio 最新 `develop` 尚未完成认证读取，当前不能声称已比较其最新代码；
- PR #229 的完整功能不会整包进入统一分支，后续按矩阵逐项吸收；
- 一个月能完成可信 MVP 纵切，但不能同时承诺成熟 SaaS、全 Provider 覆盖和电影级生成质量；
- 年底目标应以 V2 成为可持续主仓、形成多项目复用的智能生产内核为准，而不是继续维护三套等价实现。
